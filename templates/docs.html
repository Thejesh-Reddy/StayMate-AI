01 · INTRODUCTION

StayMate AI: from hotel search to booking record

StayMate AI brings hotel discovery, price comparison, booking-record management and a conversational AI assistant into one web application. Start by entering a destination or using Find hotels near me; review the returned hotel options, compare available offers, and follow the guided booking flow to save a booking record. After signing in, you can revisit your bookings, check their recorded details, and request cancellation for an eligible booking. The assistant can help search for hotels, answer questions using the site's knowledge base, and carry out supported booking lookups or cancellation steps.

This guide describes the user-facing features, the steps for using them, and the technology behind them. A saved booking record and a demo payment step are not, by themselves, proof that an external hotel has confirmed a real reservation or that money has been transferred.

What you can do here

Create and secure an account, discover hotels by destination or detected location, inspect results, compare available prices, create and review booking records, use the AI assistant, revisit chat history, and get help with supported tasks through the AI assistant.

02 · ACCOUNT & AUTHENTICATION

Create an account, sign in and recover access

1

Start registration

On the sign-in page, choose Create an account. Enter your name and email address. The application checks the email format and whether the address is already registered before sending a verification code.

2

Verify your email

Enter the one-time password (OTP) sent to your email. The current implementation gives an OTP a limited validity period and provides a Resend OTP action if you need a fresh code. An unverified email cannot complete account creation.

3

Create your password

Enter and confirm a password. The application requires at least eight characters, including an uppercase letter, a lowercase letter, a number and a special character. After successful registration, return to the sign-in page.

4

Sign in

Use your registered email and password. The password field includes a show/hide control. A successful standard-user sign-in opens the main discovery page; an administrator account opens the admin dashboard.

5

Recover a forgotten password

Select Forgot Password?, submit the email address associated with your account, and follow the reset link if one is sent. Reset links expire after a limited period and are intended for one-time use. Choose a new password that meets the password rules.

If an OTP or reset email does not arrive, check the email address and spam folder and try the available resend or reset action. Email delivery depends on the application's configured email service.

03 · HOTEL DISCOVERY

Search for hotels: every available route

Hotel discovery can be started from the main page's destination-search area or from the floating AI assistant. A search needs a destination and valid stay dates; the interface may ask for guest and room details as the conversation progresses.

A

Search a destination manually

Open Search a destination on the main page and start typing a city, town or area in India. Choose a result from the location suggestions rather than leaving an unresolved text entry. Then start the hotel search. If you type the destination in the assistant, it can resolve the place and begin the same discovery flow.

B

Use the “Find hotels near me” button

Select Find hotels near me on the home page. If the browser requests location permission, allow it to use your device's location. The application attempts browser geolocation, resolves the coordinates to a readable place, and uses that location for hotel discovery. If precise location is unavailable or denied, the application can try its configured approximate IP-location fallback. If automatic location cannot be resolved, enter a destination manually.

C

Ask the AI assistant to find hotels

Open the floating STAYMATE AI assistant and send a request such as “Find hotels in Ooty”, “Find hotels in Chittoor”, or “Find hotels near me”. A named place starts a destination search; a nearby request starts the current-location flow where available. If details are missing, answer the assistant's follow-up questions.

Stay dates, guests and rooms

Hotel availability and prices depend on the requested stay. The discovery flow uses check-in and check-out dates, adult and child counts, and room count. The application may start with temporary default search dates and default guest/room values; check the search details and update them when the interface asks. For a booking, confirm the actual dates and guest details in the booking form rather than assuming discovery defaults are final.

Location permission is optional

You can still search by entering a destination. Location-based search needs browser/device location access or a successful configured fallback; it cannot guarantee an exact location when those services are unavailable.

04 · HOTEL RESULTS

Review results and request more hotels

  • Review the hotel cards returned for your selected destination and stay details. Depending on the provider response, cards may show the hotel name, address/location, image, rating, price or other available property details.
  • Use Load more hotels when the button appears to request another set of results. More results depend on the provider's available data and pagination response.
  • From the main discovery results, use View Prices to open the price-comparison page for a hotel.
  • From the floating assistant, use a hotel's View Prices action to continue to the comparison/booking flow. When a booking is started from the assistant, the subsequent booking steps are shown inside the assistant conversation.
  • Hotel descriptions, ratings, offers and availability are provider-supplied information. Review the current details and provider terms before making a decision.
05 · PRICE COMPARISON

Compare hotel offers

The Compare Prices page displays available offers for the selected property and stay details. The page may show provider deals with a View Deal link when a booking URL is available, or a deal-unavailable state when it is not.

  1. Choose View Prices on a hotel result.
  2. Review the hotel summary and the stay information used for the comparison.
  3. Compare the available rates and offer links returned by the hotel-data provider.
  4. Choose a provider's View Deal link to continue on that provider's website, or choose Book with StayMate to use the application's internal booking-record flow.

The lowest displayed price is not a guarantee that the same price will remain available. Provider offers can change or become unavailable after the comparison page loads.

06 · BOOKING FLOW

Understand the StayMate booking steps

Choose Book with StayMate (or the relevant booking action) to open the guided booking flow. The main page and the floating assistant support the same general steps; assistant-originated booking steps remain in the assistant conversation.

1

Booking details

Enter the guest name and mobile number, confirm check-in and check-out dates, and provide the adult/child and room counts requested by the form. Review the selected hotel before continuing.

2

Billing summary

Review the rate, number of nights, room count and displayed total. The application calculates the subtotal from the nightly rate, stay duration and rooms, and includes the tax value supplied to the flow where applicable.

3

Select a payment method

The demo interface offers UPI, Credit / Debit Card and Net Banking. Select the method and continue through the demo payment step.

4

Review the result

After submission, the application displays the booking result and booking reference when the request succeeds. Keep the reference so you can distinguish bookings for the same hotel or different dates.

Demo payment and reservation status

The current project labels its payment step as demo processing. A saved StayMate booking record does not prove that a real payment was processed or that an external hotel confirmed a reservation. For a real stay, verify the reservation and payment directly with the relevant provider until a production booking and payment integration is implemented.

07 · BOOKING MANAGEMENT

My Bookings: view and identify your records

Sign in with the account used to create the booking, then choose My Bookings from the profile menu or open the My Bookings page. The page lists records associated with the authenticated account, newest first.

Booking cards can display the hotel, booking reference, stay dates, guest/room information, amount, payment method and recorded status when those fields are available. Use the unique booking reference and check-in/check-out dates to distinguish multiple bookings at the same property.

Ask the AI assistant for a booking view

“Show my bookings”“Show my upcoming bookings”“Show my confirmed bookings”“Show my cancelled bookings”“Show my bookings paid with UPI”

The assistant supports booking-list actions for all bookings, upcoming bookings, confirmed bookings and cancelled bookings. Payment-method filtering is dependent on the classifier's extracted payment information and the current filtering implementation. If a requested filter does not appear to work, use the My Bookings page to inspect the stored records and report the issue rather than assuming the filter was applied.

08 · CANCELLATION

Cancel the correct booking

  1. Sign in and ask the assistant to cancel a booking, or use the available booking-management cancellation action.
  2. If the assistant lists more than one eligible booking, choose the correct list number or enter its booking reference. This is especially important when the same hotel has multiple bookings for different dates.
  3. Review the hotel name, reference, check-in/check-out dates and total shown by the assistant.
  4. Reply Yes only when you want to cancel that exact booking. Reply No to leave it unchanged.
  5. Check the final response and My Bookings status. A cancelled record should not be offered for cancellation again.
Cancellation and refunds

The application checks booking ownership and cancellation eligibility. Refund conditions depend on the booking and any external provider's terms. Do not assume a refund has been issued just because a booking record changes to cancelled.

09 · PROFILE & SIGN-OUT

Profile and account navigation

  • Open the profile menu from the main page to see the signed-in user's displayed name and email and navigate to My Bookings.
  • The My Profile page displays the account identity information available to the application and provides navigation to bookings and back to StayMate AI.
  • Use Logout to end the current session. The application clears the server-side session and redirects to the sign-in page.
  • Protected pages such as the main discovery page, profile and My Bookings require authentication; sign in again if your session is no longer active.
10 · AI ASSISTANT

What the floating AI assistant can do

Open the floating STAYMATE AI panel from the main page. You can type a request, submit it, use the suggested FAQ prompts, close the panel and reopen it later. The assistant classifies requests and routes them to the appropriate supported action or the knowledge-base answer service.

Knowledge-base help

“What is the cancellation policy?”

  • Intent classification: a hosted Qwen classifier accessed through the configured Groq API determines whether the request is a booking action, hotel search, clarification or informational question.
  • Booking actions: supported booking lookups use the signed-in user's account. Cancellation requires a separate selection and confirmation flow.
  • Follow-up questions: the assistant can ask for missing or ambiguous information and use the current conversation context to continue the task.
  • Knowledge-base answers: policy and FAQ questions are answered using relevant passages retrieved from the project's indexed content.
  • Hotel results: when hotel search is started in the assistant, results and the available View Prices action are presented in the assistant experience; the booking flow can continue there.

The assistant can only perform actions implemented by the application. It should not be treated as a general-purpose booking agent for external hotel websites or as proof that a payment or external reservation was completed.

11 · CONVERSATION HISTORY

Past chats, continue and new chat

  • Use Past chats in the assistant to reopen a saved conversation.
  • When past-chat actions are shown, choose Continue to carry on with that conversation or New Chat to start a fresh conversation.
  • New Chat opens the assistant's default welcome message and suggested questions, rather than continuing the old conversation.
  • The browser stores assistant conversation sessions in local storage. This is browser-specific history; it is not the same as a server-side booking record and may not follow you to another browser or device.
  • Close the assistant panel when you are finished. Closing the panel is different from logging out of your StayMate account.
12 · PRIVACY & ACCOUNT SAFETY

Protect your account and information

  • Keep passwords, OTPs, password-reset links and account recovery information private.
  • Sign out when using a shared device and avoid saving credentials on public computers.
  • Use the account associated with a booking to access its personal details. Do not share booking references publicly if they expose information you want to keep private.
  • Grant browser location permission only if you want to use the near-me search. You can instead enter a destination manually.
  • Do not paste passwords, one-time codes, payment credentials or secret API keys into the assistant.
  • Official privacy notices and provider terms should be consulted where published; this user guide is not a substitute for a formal privacy policy.
13 · TECHNICAL OVERVIEW

How StayMate AI works behind the scenes

StayMate AI combines a responsive website, a Python web server, a database and AI-powered services. Each part has a clear responsibility: the interface guides the user, the backend applies application rules, the database stores account and booking records, and external services provide hotel information, email delivery and AI classification.

Website and interaction layerThe pages are rendered with Flask templates and Jinja, styled with CSS, and made interactive with browser-side JavaScript. This layer supports registration, sign-in, location suggestions, hotel cards, price comparison, booking forms, profile navigation, the floating assistant and saved chat history.
Application and business-logic layerPython and Flask receive requests from the browser, validate inputs, apply booking rules and coordinate the database and configured services. Protected actions check the active session and, where needed, the user's role or ownership of a booking.
Authentication and account protectionEmail verification uses one-time codes. Passwords are stored as hashes, password recovery uses time-limited reset links, and sessions identify signed-in users. Sensitive account actions are restricted to authenticated users.
Data layerMongoDB Atlas stores user accounts and booking records. Booking lookups are scoped to the authenticated account, and cancellation requests verify ownership and eligibility. Assistant chat history is stored in the browser, so it is separate from permanent booking records.
AI intent classificationThe assistant sends the latest message and relevant conversation context to a Qwen model hosted through Groq. The model classifies the request and extracts useful details; the backend then decides which supported action to run. The model does not directly write to the database or independently confirm that a booking has changed.
Knowledge-base answers (RAG)Retrieval-augmented generation converts the user's question into an embedding, searches a FAISS vector index, and retrieves relevant passages from the project's FAQ and policy knowledge base. The current service builds its response from retrieved content and can return source metadata. Its answer quality depends on the coverage and relevance of the indexed material.
Hotel discovery and location servicesHotel searches use configured hotel-provider data to return properties, offers and available provider links. Location suggestions and reverse geocoding use Photon, while browser geolocation can provide device coordinates. An approximate IP-based location may be used as a fallback when available.
Email delivery and deploymentTransactional emails are sent through the Brevo HTTPS API, including signup OTPs, password-reset messages, booking confirmations with PDF attachments, and cancellation confirmations. The application sends HTTPS requests to Brevo rather than connecting to Gmail SMTP. Render hosts the deployed web application. Local environment variables and Render environment variables are configured separately, so each required credential must be set securely where the application runs.
How responsibilities are separated

The browser presents the workflow, Flask validates and coordinates it, MongoDB stores account and booking data, and external services supply specialist capabilities. This separation helps the application keep access control and booking decisions on the server instead of trusting the browser or AI model alone.

14 · INTEGRATIONS & CONFIGURATION

Services the application depends on

MongoDB AtlasStores account and booking data. The MongoDB URI and credentials must be set in the deployment environment and the database network access rules must allow the service to connect.
Groq APIHosts the configured Qwen intent-classification model. A valid GROQ_API_KEY is required for assistant intent classification. If it is missing or invalid, assistant action routing can fail even when other site pages still load.
SerpApi / Google HotelsProvides hotel search and property details. The application requires the configured SERPAPI_KEY for these endpoints.
Photon geocoding and browser locationProvides location suggestions and reverse-geocoding support; browser geolocation requires user permission. Approximate IP lookup may be used when available.
Brevo transactional email APISends signup OTPs, password-reset emails, booking confirmations with PDF attachments, and cancellation emails through Brevo’s HTTPS API endpoint https://api.brevo.com/v3/smtp/email. Configure BREVO_API_KEY, MAIL_DEFAULT_SENDER and MAIL_SENDER_NAME in the environment. The sender email must be a valid sender configured and verified in Brevo. EMAIL_PROVIDER=brevo may be kept as a descriptive setting; the current email service reads the Brevo API key and sender variables directly.
RenderHosts the web service. Environment variables must be configured in the Render service separately from local development. Never put secrets in the ZIP, public repository, HTML or client-side JavaScript.

Brevo environment configuration

Add the following placeholders to .env.example. Put your real API key and verified sender address in your local .env file and in Render’s Environment settings; do not commit secrets to GitHub.

EMAIL_PROVIDER=brevo
BREVO_API_KEY=your_brevo_api_key_here
MAIL_DEFAULT_SENDER=your_verified_sender@example.com
MAIL_SENDER_NAME=STAYMATE AI
Brevo setup and troubleshooting

Generate a regular Brevo API key; MCP does not need to be enabled for sending email. Add and verify the sender under Brevo’s sender settings. MAIL_DEFAULT_SENDER must contain the email address alone, for example sender@example.com, not a combined value such as StayMate AI <sender@example.com>. The sender display name belongs in MAIL_SENDER_NAME. If the API returns “valid sender email required,” check the exact sender value loaded by the application, remove duplicate environment entries, and restart Flask after editing .env. Make sure requests is installed through requirements.txt.

15 · IMPORTANT LIMITATIONS

What users should and should not assume

  • Hotel availability: search results reflect external provider data at the time of the request and can change.
  • Provider links: a provider offer is useful for continuing to that provider, but StayMate does not control the provider's final availability or checkout.
  • Internal booking record: the application can store a booking record and reference; this alone is not proof of a confirmed external reservation.
  • Demo payment: the current project describes demo payment processing and must not be represented as a live payment gateway.
  • AI answers: the classifier routes requests and the RAG service retrieves project knowledge. Verify important booking or payment details against the stored record and relevant provider.
  • Location: geolocation depends on browser permission and device support; IP location is approximate and may be unavailable.
  • External service configuration: hotel search, AI classification, email and database operations depend on valid credentials and network connectivity in the deployed environment.
